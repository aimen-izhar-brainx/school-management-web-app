# T-012: RolesGuard + @Roles decorator (backend infrastructure)
- Milestone: M1
- Depends on: none
- Use cases: UC-04 (enabling infrastructure)

## Goal
Add a reusable `RolesGuard` + `@Roles()` decorator so any endpoint can be locked to specific roles (starting with admin-only writes), reading the `role` already present in the JWT payload. No feature endpoints exist yet — this ticket proves the mechanism works in isolation; concrete UC-04/12/17/21 acceptance criteria are verified in the tickets that add the real endpoints.

## Definition of Done
- [x] A `RolesGuard` exists that reads `role` from the authenticated request (populated by the existing `JwtStrategy`) and allows/denies based on a `@Roles(...)` decorator on the route handler.
- [x] Unit test: a route guarded with `@Roles('admin')` allows a request with `role: 'admin'` and rejects (403) requests with `role: 'teacher'` or `role: 'student'`.
- [x] Unit test: an unauthenticated request (no/invalid JWT) is rejected with 401 by the existing `JwtAuthGuard`, confirming the guard chain (`JwtAuthGuard` + `RolesGuard`) composes correctly.
- [x] All tests pass. Reviewer approved. Verifier passed.

## Technical notes
- New files: `backend/src/common/guards/roles.guard.ts`, `backend/src/common/decorators/roles.decorator.ts`.
- `RolesGuard` reads `request.user.role` — matches the `JwtPayload` shape already returned by `backend/src/auth/jwt.strategy.ts` (`validate()` returns `{ sub, email, role }`, attached by Passport as `request.user`).
- Apply guards together as `@UseGuards(JwtAuthGuard, RolesGuard)` on controllers/handlers (JwtAuthGuard already exists at `backend/src/auth/jwt-auth.guard.ts`).
- Test with a throwaway controller/route in the guard's own spec file (e.g. `backend/src/common/guards/roles.guard.spec.ts`), not a real feature controller — those come in T-013 onward.
