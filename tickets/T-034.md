# T-034: Admin attendance edit (audited) + browse endpoint (backend)
- Milestone: M2
- Depends on: T-032
- Use cases: UC-05, UC-07

## Goal
Let Admin edit any section's attendance for any day — locked or not — with every changed status recorded in an audit log, and let Admin fetch any section's attendance regardless of ownership.

## Definition of Done (copied from use cases)
- [x] AC-05.1 Given a locked (past) day with recorded attendance, when Admin changes a student's status and saves, then the new status is persisted and an audit entry is created.
- [x] AC-05.2 Given today's attendance was already submitted by the class teacher, when Admin changes a status, then it is saved and an audit entry is created too — unlike the teacher's own same-day edits, which are never logged.
- [x] UC-05-E1: Admin "edits" a student to the same status it already had → no audit entry created (no real change).
- [x] UC-05-E2: Admin attempts to edit a section/date with no existing session → rejected with "not marked yet" (admin edits existing records, doesn't create original submissions).
- [x] UC-05-E3: Two admins edit the same day around the same time → both edits are applied in order, each creating its own audit row; no silently lost update.
- [x] AC-07.1 Given the caller is not Admin, when they call the admin edit endpoint for any section, then 403 is returned and nothing changes.
- [x] AC-07.2 Given a Teacher who is not that section's class teacher, when they call the admin browse endpoint for that section, then 403 is returned.
- [x] UC-07-E1: A class teacher viewing their own section via their own (M1) endpoint is unaffected — that's a different, allowed endpoint.
- [x] All tests pass. Reviewer approved. Verifier passed.

## Technical notes
- Prisma: add `model AttendanceEdit` (`sessionId`, `studentId`, `fromStatus`, `toStatus`, `editedById`, `editedAt`) per `docs/plan.md`'s data model. Migration.
- New endpoint in `attendance.controller.ts`, guarded `@Roles('admin')`:
  - `PATCH /attendance/admin/sections/:sectionId/days/:date` — body `{ entries: { studentId, status }[] }`. Service: 404 if section unknown, 404/"not marked yet" if no `AttendanceSession` exists for that section+date (UC-05-E2), otherwise for each entry whose `status` differs from the stored one: update it and insert one `AttendanceEdit` row (`fromStatus`, `toStatus`, `editedById: req.user.id`, `editedAt: now`); entries with an unchanged status are skipped (UC-05-E1, no audit row). No date restriction — works for today or any past day (AC-05.1/AC-05.2).
  - `GET /attendance/admin/sections/:sectionId/days/:date` — admin-only, same shape as the M1 `GET` but with no ownership check and includes the `edits` (audit log) in the response.
- Concurrency (UC-05-E3): wrap the per-entry compare-and-update-and-log in a single DB transaction per request so two overlapping admin saves each apply cleanly and each produce their own audit rows (no lost-update merging of the two payload sent bodies — last request's writes simply happen after the first's).
- Role separation: keep this as a separate `/attendance/admin/...` route rather than overloading the M1 teacher route, so `@Roles('admin')` vs `@Roles('teacher')` guards stay simple and AC-07.1/AC-07.2 are trivial route-level checks. Confirm in a test that the T-032 teacher endpoints are untouched and still 403 a non-owning teacher and 200 the owning teacher (UC-07-E1 — a regression check, not new behavior).
