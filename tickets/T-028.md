# T-028: Delete class with sections, subjects or students (backend)
- Milestone: M2
- Depends on: T-016, T-017
- Use cases: UC-23, UC-03

## Goal
Make `DELETE /classes/:id` safe once a class has sections, subject assignments and students. Its sections and subject assignments are removed and its students are unassigned (never deleted). Add a read endpoint that returns the counts for the confirmation dialog.

## Definition of Done (copied from use cases)
- [ ] AC-23.1 Given a class with sections, subject assignments or assigned students, when Admin clicks "Delete class", then the confirmation shows the counts, e.g. "Deleting Grade 5 will also delete 2 sections and 4 subject assignments. 30 students will be unassigned from their section."
- [ ] AC-23.2 Given Admin confirms, when the request completes, then the class, its sections, its subject assignments and its sections' timetable entries are all gone, both immediately and after reload.
- [ ] AC-23.3 Given students were assigned to those sections, when the class is deleted, then the student accounts still exist with no section; on "My Timetable" they see the UC-20 message.
- [ ] UC-23-E2: A student is assigned to one of the class's sections after the dialog opens but before Admin confirms → that student is also unassigned, not deleted. The counts in the dialog may be out of date, but the result is still correct.
- [ ] AC-04.1 Given a logged-in Teacher, when calling create/rename/delete, then responds 403 Forbidden, no data changes.
- [ ] AC-04.2 Given a logged-in Student, when calling create/rename/delete, then responds 403 Forbidden, no data changes.
- [ ] All tests pass. Reviewer approved. Verifier passed.

## Technical notes
- Backend scope of each AC:
  - AC-23.1: the backend provides the counts. The dialog text is in T-029.
  - AC-23.2: the backend covers sections and subject assignments. Timetable entries are checked in T-022, once `TimetableEntry` exists.
  - AC-23.3: the backend covers the student staying with `sectionId = null`. The "My Timetable" message is checked in T-024/T-025.
- New endpoint: `GET /classes/:id/delete-impact` (admin-only) → `{ className, sections, subjectAssignments, students }`.
- `DELETE /classes/:id`: do it in one transaction. First clear `User.sectionId` where the section belongs to this class, then delete the class (`Section` and `ClassSubject` cascade by `onDelete: Cascade`). The `User.sectionId` relation should use `onDelete: SetNull`. If T-017 used an app-level unassign instead, make sure the class-level cascade can't fail with a foreign-key error (UC-23-E2 depends on this).
- Return 404 "This class no longer exists." for an unknown id (UC-03-E1 relies on this).
