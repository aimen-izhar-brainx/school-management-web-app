# T-016: Subject catalog + class-subject-teacher assignment (backend)
- Milestone: M2
- Depends on: T-013, T-015
- Use cases: UC-09, UC-10, UC-12 (partial)

## Goal
Add a global `Subject` catalog (own `subjects` module) and the `ClassSubject` join model that assigns a subject + exactly one teacher to a class (endpoints live in the existing `classes` module, per `docs/plan.md`'s architecture).

## Definition of Done
- [ ] AC-09.1 Given a valid, unique subject name, when created, then it appears in the catalog and can subsequently be assigned to any class.
- [ ] AC-09.2 Given an empty subject name, when submitted, then responds 400 with "Please enter a subject name." and creates nothing.
- [ ] AC-09.3 Given a subject name that already exists (case-insensitive), when submitted, then responds 400 with "This subject already exists." and creates nothing.
- [ ] UC-09-E1 Given a subject currently assigned to one or more classes (has `ClassSubject` rows), when deletion is attempted, then responds 400 with "This subject is in use and can't be deleted." and nothing is deleted.
- [ ] AC-10.1 Given a subject is added to a class, when fetched again, then it appears in that class's subject list.
- [ ] AC-10.2 Given a teacher is assigned to a class-subject, when a different teacher is assigned afterward, then the assignment is replaced (exactly one teacher per class-subject at a time, never two).
- [ ] AC-10.3 Given the teacher-assignment endpoint is called with a non-teacher user id, then it is rejected (reuses the `role=teacher` filtering from T-015's users-by-role endpoint for validation).
- [ ] AC-10.4 Given a subject already assigned to a class, when the same subject is submitted again for that class, then it is not duplicated (responds 400 or is a no-op, not a second row).
- [ ] UC-10-E1 Given a class-subject with no teacher assigned (`teacherId: null`), then it is a valid, persisted state (it just can't be used in the timetable builder yet — enforced in T-021).
- [ ] AC-12.1 Given a logged-in Teacher or Student, when calling any subject-catalog or class-subject write endpoint, then responds 403 Forbidden and no data changes.
- [ ] UC-12-E1 Given no token or an expired token, when calling any of these endpoints, then responds 401 Unauthorized.
- [ ] All tests pass. Reviewer approved. Verifier passed.

## Technical notes
- Prisma: add `model Subject { id, name @unique, createdAt }` and `model ClassSubject { id, classId -> Class (onDelete: Cascade), subjectId -> Subject, teacherId -> User? ("SubjectTeacher"), @@unique([classId, subjectId]) }` per `docs/plan.md`. Migration required.
- New module: `backend/src/subjects/` for catalog CRUD (`GET /subjects`, `POST /subjects`, `DELETE /subjects/:id`).
- Extend `backend/src/classes/` module with `POST /classes/:classId/subjects` (body: `{ subjectId }`), `PATCH /classes/:classId/subjects/:id/teacher` (body: `{ teacherId: string | null }`), `DELETE /classes/:classId/subjects/:id`.
- `DELETE /classes/:classId/subjects/:id` gets an additional "blocked if timetable entries exist" check in T-021 (UC-10-E2), once `TimetableEntry` exists — not part of this ticket.
- Apply `@UseGuards(JwtAuthGuard, RolesGuard)` + `@Roles('admin')` on all write endpoints in both modules.
- Subject rename (`PATCH /subjects/:id`) and the full UC-22 delete rules come in T-026, not here. Keep `ClassSubject.subject` as the default `Restrict` relation (no cascade) so T-026's UC-22-E3 holds.
