# T-022: Teacher double-booking conflict detection (backend)
- Milestone: M3
- Depends on: T-021, T-028
- Use cases: UC-14, UC-23 (partial)

## Goal
Add the DB-level unique constraint plus a service-layer check so a teacher can never be scheduled in two different sections at the same day + period, with a clear, specific error message. This ticket also checks that deleting a class (T-028) removes its timetable entries and frees those teachers' slots.

## Definition of Done
- [ ] AC-14.1 Given teacher X is already scheduled for Section A, Monday, Period 1, when Admin tries to schedule teacher X for Section B at the same Monday, Period 1, then responds 400 with "Teacher is already scheduled for [Section A] at this time." and does not save.
- [ ] AC-14.2 Given the conflict in AC-14.1 is rejected, when Section A's timetable is fetched, then it is unchanged.
- [ ] AC-14.3 Given two different teachers, when scheduled in different sections at the same day + period, then both are saved without conflict (conflict is scoped per teacher, not per slot globally).
- [ ] UC-14-E1 Given two concurrent requests try to book the same teacher into two different sections for the same slot, when both reach the server, then only one succeeds; the second gets the AC-14.1 conflict error, enforced by the DB unique constraint (`[teacherId, periodId, dayOfWeek]`), not only an application-level pre-check.
- [ ] UC-14-E2 Given Admin replaces a teacher's existing slot with a new subject/teacher in the same section/slot (an update, not a new booking), when saved, then it does not falsely conflict with the entry being replaced.
- [ ] AC-23.2 (timetable part, completed here) Given Admin confirms, when the request completes, then the class, its sections, its subject assignments and its sections' timetable entries are all gone, both immediately and after reload.
- [ ] AC-23.4 Given teachers were scheduled in those sections, when the class is deleted, then those day/period slots are free and the teachers can be booked into other sections at those times without a conflict.
- [ ] All tests pass. Reviewer approved. Verifier passed.

## Technical notes
- Prisma: add `@@unique([teacherId, periodId, dayOfWeek])` to `TimetableEntry` (from T-021) as the source-of-truth constraint. Migration required.
- In `backend/src/timetable/`, before writing, query for an existing `TimetableEntry` with the same `teacherId` + `periodId` + `dayOfWeek` (excluding the row being updated, for UC-14-E2) and return the specific section-name error; still catch the DB unique-constraint violation (P2002) as a fallback for the race condition in UC-14-E1, in case two requests pass the pre-check simultaneously.
- AC-23.2/AC-23.4 need no new code: `TimetableEntry.section` already uses `onDelete: Cascade` (T-021), and class → section cascades (T-015/T-028). Add a test that deletes a class, then books the same teacher at the same slot in another class's section and expects it to succeed.
- Include the conflicting section's name in the error response body so the frontend (T-023) can render AC-14.1's exact message.
