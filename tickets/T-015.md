# T-015: Section CRUD + class-teacher assignment (backend)
- Milestone: M2
- Depends on: T-013
- Use cases: UC-06, UC-07 (partial), UC-08, UC-12 (partial)

## Goal
Add the `Section` Prisma model (nested under `Class`) with CRUD endpoints and class-teacher assignment, inside the existing `classes` module per the plan's architecture. Also add a shared, admin-only "list users by role" endpoint, needed here for the teacher dropdown and reused by later tickets.

## Definition of Done
- [x] AC-06.2 Given a section was created, when fetched again, then it persists.
- [x] AC-06.3 Given an empty section name, when submitted, then responds 400 with "Please enter a section name." and creates nothing.
- [x] AC-06.4 Given a section name that already exists in the same class (case-insensitive), when submitted, then responds 400 with "This section already exists." and creates nothing.
- [x] UC-06-E1 Given the same section name in a *different* class, when submitted, then it is allowed (uniqueness is scoped to `[classId, name]`, not global).
- [x] UC-06-E2 Given a whitespace-only name, when submitted, then treated as empty and rejected as AC-06.3.
- [x] UC-06-E3 Given two concurrent create requests for the same section name in the same class, when both reach the server, then only one is created; the second fails with the AC-06.4 error (DB unique constraint on `[classId, name]`).
- [x] AC-07.1 Given a section is deleted, when fetched again (list/get on its class), then it is gone.
- [x] AC-08.1 Given a teacher is assigned as class teacher, when fetched again, then the assignment persists.
- [x] AC-08.2 Given the "list users by role" endpoint is called with `role=teacher`, then only Users with `role: teacher` are returned.
- [x] AC-08.3 Given a section has a class teacher, when the assignment is cleared (set to null), then it is removed.
- [x] UC-08-E2 Given the same teacher assigned as class teacher for two different sections, then both assignments succeed (not restricted).
- [x] AC-12.1 Given a logged-in Teacher or Student, when calling any section-related write endpoint, then responds 403 Forbidden and no data changes.
- [x] UC-12-E1 Given no token or an expired token, when calling any section-related endpoint, then responds 401 Unauthorized.
- [x] All tests pass. Reviewer approved. Verifier passed.

## Technical notes
- Prisma: add `model Section { id, name, classId -> Class (onDelete: Cascade), classTeacherId -> User? ("SectionClassTeacher"), createdAt, updatedAt, @@unique([classId, name]) }` per `docs/plan.md`'s data model. Migration required.
- Extend `backend/src/classes/` module (not a new top-level module, per `docs/plan.md`'s architecture): add nested endpoints `POST /classes/:classId/sections`, `PATCH /classes/:classId/sections/:id`, `DELETE /classes/:classId/sections/:id`, `PATCH /classes/:classId/sections/:id/class-teacher` (body: `{ teacherId: string | null }`).
- Add `GET /users?role=teacher|student` (admin-only) to `backend/src/users/` (extends the existing minimal `UsersService`) — reused by T-016, T-017, T-019.
- Apply `@UseGuards(JwtAuthGuard, RolesGuard)` + `@Roles('admin')` on all new write endpoints, consistent with T-013/T-012.
- `AC-07.1`'s full behavior (cascading student unassignment, timetable-entry cascade) is completed in T-017 and T-021 respectively, once those fields/models exist — this ticket only needs the basic `Section` row deletion to work correctly.
