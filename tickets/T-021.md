# T-021: TimetableEntry CRUD API (backend, no conflict checking yet)
- Milestone: M3
- Depends on: T-015, T-016, T-020
- Use cases: UC-13, UC-15, UC-16 (partial), UC-17

## Goal
Add the `TimetableEntry` Prisma model and a `timetable` module with basic CRUD (assign/clear a subject+teacher at a section's day/period slot, view a section's grid), enforcing admin-only writes. Conflict detection is deliberately deferred to T-022 so this ticket stays reviewable on its own.

## Definition of Done
- [x] AC-13.1 Given a subject with a teacher already assigned to the class (T-016), when placed in a slot, then the slot persists with subject + teacher.
- [x] AC-13.2 Given the valid-subjects list for a slot, when queried, then only subjects already assigned to this class (T-016) are returned — not the full subject catalog.
- [x] AC-13.3 Given a class-subject with no teacher assigned, when Admin tries to place it in a slot, then responds 400 with "Assign a teacher to this subject first." and the slot is not saved.
- [x] UC-13-E1 Given a subject's assigned teacher is changed afterward (T-016), when existing timetable entries for that subject are checked, then they keep their original teacher (no retroactive update).
- [x] UC-13-E2 Given a subject already placed in one slot, when placed in a second slot for the same section, then both are allowed (no per-day/week limit in v1).
- [x] AC-15.1 Given a filled slot, when cleared, then it is removed; a subsequent fetch shows it as empty.
- [x] AC-15.2 Given a slot is cleared, then that teacher's day/period becomes available for a different section (no longer blocking a new assignment there).
- [x] UC-15-E1 Given an already-empty slot, when "clear" is called on it, then it is a no-op, not an error.
- [x] AC-16.1 Given a section with no entries yet, when its grid is fetched, then the response represents all non-break slots as empty (no error).
- [x] AC-16.2 Given a section with existing entries, when its grid is fetched, then each entry includes subject name + teacher name.
- [x] AC-17.1 Given a logged-in Teacher or Student, when calling the create/update/delete timetable-entry endpoint, then responds 403 Forbidden and no data changes.
- [x] UC-17-E1 Given no token or an expired token, when calling any timetable endpoint, then responds 401 Unauthorized.
- [x] AC-07.3 (from UC-07, completed here) Given the section had timetable entries, when the section is deleted, then its timetable entries are deleted too (cascade).
- [x] UC-10-E2 (from UC-10, completed here) Given a class-subject has existing timetable entries, when its removal from the class is attempted (T-016's `DELETE /classes/:classId/subjects/:id`), then responds 400 with "This subject has timetable entries for this class. Remove them first." and nothing is removed.
- [x] All tests pass. Reviewer approved. Verifier passed.

## Technical notes
- Prisma: add `model TimetableEntry { id, sectionId -> Section (onDelete: Cascade), periodId -> Period, dayOfWeek: DayOfWeek, subjectId -> Subject, teacherId -> User ("EntryTeacher"), @@unique([sectionId, periodId, dayOfWeek]) }` per `docs/plan.md`. (The second unique constraint, `@@unique([teacherId, periodId, dayOfWeek])`, is added in T-022 together with the conflict-handling logic that relies on it.) Migration required.
- New module: `backend/src/timetable/` — `GET /sections/:sectionId/timetable`, `PUT /sections/:sectionId/timetable/:periodId/:dayOfWeek` (upsert, body: `{ subjectId }`, server looks up the teacher from the class-subject assignment), `DELETE /sections/:sectionId/timetable/:periodId/:dayOfWeek`.
- Retrofit `backend/src/classes/` subject-removal endpoint (from T-016) with the UC-10-E2 check (query `TimetableEntry` for that `classId` + `subjectId` before allowing removal).
- Apply `@UseGuards(JwtAuthGuard, RolesGuard)` + `@Roles('admin')` on all write endpoints.
