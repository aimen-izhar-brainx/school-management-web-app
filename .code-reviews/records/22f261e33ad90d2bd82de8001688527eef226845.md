## Summary

Stack: NestJS (backend) + React (frontend), Prisma/Postgres. The change set adds two backend features and moves two frontend pages onto them:
- **People module** (`/people`, admin-only): create/list/update/delete/resend-invite for teachers, students and parents, with new `User` profile columns and a parent-child link.
- **Notices module** (`/notices`): school-wide or class-targeted notices with audience filtering, author-only delete for teachers, and BCC email notification.
- Frontend: `AdminCreatePage` now uses the real API through `PeopleSection`/`PersonForm`. `NoticeBoardPage` uses the API, with a new `LatestNotices` dashboard card. Static `data/notices.ts` is removed.
- Test infrastructure: a separate `_test` database and global cleanup. The throttler default is raised from 20 to 300, and `/auth` keeps 20 through a controller-level `@Throttle`.

Auth, role guards, DTO validation (`whitelist`, mass-assignment-safe DTOs), audience scoping and the Prisma error mapping (409/404/400) are done well. There are no cross-repo contract mismatches: the frontend `Person` and `Notice` shapes match the service `present()` output. The shared hardcoded default password and the unbounded list queries from the first pass have since been fixed.

## Findings

### Critical (0)
- **backend/src/people/people.service.ts:15** — Every account created through `POST /people` is given the hardcoded password `12345678` (hashed at line 86). Anyone who knows or guesses a new user's email can sign in as that user, whether a teacher, a parent (child data) or a student, before the invite link is used or even if it is never used. The code is marked TEMPORARY, but nothing enforces its removal, and `resendInvite` does not reset the password either. *(security)*
  - status: fixed
  - dev_reasoning: N/A
  - ai_reasoning: Fixed: the hardcoded password is gone. `create` now hashes `generateRawToken()` (people.service.ts:85-86), which is never disclosed, so the invite link is the only way in.

### High (0)
- **backend/src/notices/notices.service.ts:51** — `list()` is unbounded when `limit` is omitted. `NoticeBoardPage` calls `/notices` with no limit, and admins and teachers get every notice ever posted. `PeopleService.list` (people.service.ts:70) is likewise unpaginated and returns every user of a role, with joined section, parent and children. Both grow with the school and are sent whole to the browser. *(performance)*
  - status: fixed
  - dev_reasoning: N/A
  - ai_reasoning: Fixed: `NoticesService.list` now applies `take: limit ?? DEFAULT_LIST_LIMIT`, and `PeopleService.list` caps results with `MAX_LIST_ROWS = 500`. Cursor pagination is still absent, but the response is now bounded.

### Medium (1)
- **backend/src/notices/notices.service.ts:89** — Notice emails are sent from a fire-and-forget promise inside the request handler. It runs up to N/50 sequential SMTP sends for a school-wide notice, with no retry, no backoff and no queue. It is lost if the process restarts mid-send, and it holds the event loop and SMTP connections on the API process. `PeopleService.sendInvite` has the same pattern. *(reliability)*
  - status: skipped
  - dev_reasoning: A durable queue needs new infrastructure (Redis plus @nestjs/bullmq) that this project does not have yet. Delivery already runs in batches of 50 and failures are logged without affecting the request. To be done as a separate follow-up ticket when production email volume requires it.
  - ai_reasoning: The `.catch` logging is good. For production, move delivery to a queue (`@nestjs/bullmq`) or at least run batches with bounded concurrency. Pass IDs in the job payload and re-query recipients when the job runs.
- **frontend/src/components/PeopleSection.tsx:106** — For the student form, the picker data does `/classes` and then one `/classes/:id/sections` request per class (an N+1 from the browser). It also loads every parent through `/people?role=parent`. The load cost grows with the number of classes and parents, and a failure silently leaves the pickers empty. *(performance)*
  - status: fixed
  - dev_reasoning: N/A
  - ai_reasoning: Fixed: the pickers now use a single `/sections` call that returns class names, and a load failure sets `pickerError` which is shown above the form.
- **backend/src/people/people.service.ts:99** — `email` uniqueness is mapped to 409 correctly, but profile identifiers (`employeeId`, `rollNumber`) have no unique constraint in the schema or migration. The same employee ID or roll number can be assigned to several people, which usually breaks downstream lookups. *(data-integrity)*
  - status: fixed
  - dev_reasoning: N/A
  - ai_reasoning: Fixed: migration 20261014140000 adds a unique index on `employeeId` and on (`sectionId`, `rollNumber`), mirrored in schema.prisma.
