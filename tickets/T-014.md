# T-014: Wire ClassesPage class list to real API (frontend)
- Milestone: M1
- Depends on: T-013
- Use cases: UC-01, UC-02, UC-03, UC-04, UC-05

## Goal
Replace `ClassesPage`'s in-memory class list (`initialClasses`, local `useState`) with real calls to the `/classes` API from T-013, keeping the existing visual design but making data persist.

## Definition of Done
- [ ] AC-01.1 Given a valid, unique class name, when Admin submits the new-class form, then the class appears in the list without a full page reload.
- [ ] UC-01-E3 Given the backend is unreachable, when Admin submits the form, then a generic "Something went wrong. Please try again." error is shown and the entered text is retained in the field.
- [ ] AC-02.1 Given a valid new unique name, when Admin saves a rename, then the list/header show the new name immediately.
- [ ] UC-02-E2 Given the class was deleted by another session moments earlier, when this admin submits a rename for it, then shows "This class no longer exists." and refreshes the list.
- [ ] UC-02-E3 Given a slow network, when Admin saves a rename, then the Save button shows a loading state and is disabled until the request completes.
- [ ] AC-03.1 Given confirmation, when the delete request completes, then the class disappears from the list without reload.
- [ ] AC-03.3 Given Admin cancels the delete confirmation prompt, then no delete request is sent and the class remains.
- [ ] UC-03-E1 Given the class was already deleted by another session, when this admin confirms delete again, then shows "This class no longer exists." instead of a crash, and refreshes the list.
- [ ] UC-03-E2 Given it is the last remaining class, when deleted, then the "No classes yet." empty state renders cleanly.
- [ ] UC-03-E3 Given the backend is unreachable, when Admin confirms delete, then a generic error is shown and the class remains in the list.
- [ ] AC-04.3 Given Teacher/Student view the Classes page, then write controls (New class, Rename, Delete) are not shown or are disabled.
- [ ] AC-05.1 Given no classes exist yet, when the page loads, then it shows "No classes yet."
- [ ] UC-05-E1 Given the backend is slow or unreachable, when the page loads, then a loading indicator is shown, followed by a clear error state if the request fails.
- [ ] All tests pass. Reviewer approved. Verifier passed.

## Technical notes
- Files: `frontend/src/components/ClassesPage.tsx`, its co-located `ClassesPage.test.tsx`.
- `frontend/src/lib/http.ts` currently only exports `get`/`post` — add `patch`/`delete` methods (same `request<T>` pattern, `ApiError` already handles non-2xx responses and message extraction).
- Replace `initialClasses`/local-only `classes` state with `useEffect` + `api.get('/classes')` on mount; wire `handleAddClass`/`commitRenameClass`/`handleDeleteClass` to `api.post`/`api.patch`/`api.delete`, using `ApiError.message` for the existing error-display pattern (`classNameError`, etc.).
- Keep section/subject UI in this file as still-mocked placeholders for now — those are wired in T-018/T-019; only the class list (left column + rename/delete) becomes real in this ticket.
- Role-based control hiding (AC-04.3): the logged-in user's role is available via the existing `AuthUser`/`user` prop already passed into `ClassesPage`.
