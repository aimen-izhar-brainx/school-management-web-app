# T-026: Subject rename + delete (backend)
- Milestone: M2
- Depends on: T-016
- Use cases: UC-22, UC-09, UC-12 (partial)

## Goal
Add a rename endpoint to the subject catalog and make sure delete follows UC-22. A subject can be deleted only when no class uses it, and two admins acting at the same time can never leave a class pointing at a deleted subject.

## Definition of Done (copied from use cases)
- [ ] AC-22.1 Given a valid, unique new name, when saved, then the new name shows immediately in the catalog, in every class's subject list and in every timetable cell that uses it, and it persists after reload.
- [ ] AC-22.2 Given the name is cleared to empty, when saved, then shows "Please enter a subject name." and keeps the original name.
- [ ] AC-22.3 Given the new name already belongs to another subject (case-insensitive), when saved, then shows "This subject already exists." and the rename is not applied.
- [ ] AC-22.4 Given a subject not assigned to any class, when Admin confirms delete, then it disappears from the catalog and does not reappear after reload.
- [ ] AC-22.5 Given a subject assigned to one or more classes, when Admin confirms delete, then shows "This subject is in use and can't be deleted." and nothing is removed (same rule as UC-09-E1).
- [ ] UC-22-E1: Changing only the letter case of the subject's own name (e.g. "maths" → "Maths") succeeds and is not treated as a duplicate.
- [ ] UC-22-E3: One admin deletes a subject while another admin assigns it to a class at nearly the same time → the database keeps them consistent: either the delete fails with the in-use error, or the assignment fails because the subject no longer exists. A class never ends up with a deleted subject.
- [ ] AC-12.1 Given a logged-in Teacher or Student, when calling any M2 write endpoint, then responds 403 Forbidden, no data changes.
- [ ] All tests pass. Reviewer approved. Verifier passed.

## Technical notes
- Backend reading of the ACs: "shows <message>" means the endpoint responds 400 with that message. For AC-22.1, the backend only has to return the new name from `GET /subjects` and `GET /classes/:classId/subjects` (names are joined by `subjectId`, so nothing is copied). The UI side is in T-027, and the timetable-cell side is in T-023.
- New endpoint: `PATCH /subjects/:id` (body: `{ name }`), with the same DTO validation as create (trimmed, non-empty, max 100). Use `@UseGuards(JwtAuthGuard, RolesGuard)` + `@Roles('admin')`.
- `DELETE /subjects/:id` already exists from T-016 with the UC-09-E1 check. Confirm it responds 404 for an unknown id (needed by UC-22-E2 in T-027).
- UC-22-E3: keep the `ClassSubject.subject` relation as the default `Restrict` (no `onDelete: Cascade`). Catch Prisma `P2003` (foreign key) on delete and map it to the in-use message. Catch `P2003`/`P2025` on class-subject create and map it to a 404 "This subject no longer exists."
- Case-insensitive uniqueness when renaming: exclude the subject's own id from the duplicate check (UC-22-E1).
